# 档案匹配决策

领域含义见 [术语表](GLOSSARY.md)。后端建议的判定条件见 [MatchResult](../src-tauri/src/automation/archive_scan/matching.rs)，本文仅保留决策理由与来源。

## 决策理由

- 每次档案详情页面只展示一个具体档案，因此每条扫描记录最多匹配一个档案。同标题无法证明是同一份档案，不能让一次观察贡献多个档案的收集证据。
- 只对唯一精确命中自动建立匹配。模糊候选即使只有一个，也可能只是目录中唯一足够相近的标题，不能据此认定已经收集。
- 标题规范化、已知标题解释和模糊推荐集中在后端，使领域判断拥有同一事实来源。前端负责用户选择，保留原始观察与后端建议，以便区分自动判断和人工决定。
- 用户确认选择后，使用所选档案作为有效匹配。用户删空输入并确认后，该记录保持未匹配，即使后端原有建议是精确匹配。因此，明确的人工未选择需要与尚未作出人工决定区分。
- 正文首行帮助用户区分同名档案。我们只为手动选定的部分档案补充这项信息，避免资源文件过大或产生大量无关改动。自动正文判别另由后端专用逻辑维护，不依赖这项展示信息。

## 参考正文来源

两个「挂在竹子上的字条」具有相同标题和图标，正文可以提供人工区分依据。关联经 `PrtsAllItem.contentId → RichContentTable.contentList → I18nTextTable_CN/EN` 核实：

- `nar_paper_map02_93_1` 经 `text_sm2l3m1_1` 关联正文。中文首行为「先祖保佑我家那口子」，英文首行为「Protect my family」。
- `nar_paper_map02_93_2` 经 `text_sm2l3m1_2` 关联正文。中文首行为「保佑寨子■■■■」，英文首行为「Protect the ■■■■ Stockade」。遮罩共四个字符，按源文本保留。

正文来自游戏解包数据。生成方式与类型传递见 [数据管线](data-pipeline.md)。

## 正文判别

正文仅用于确认分类内标题精确命中的已知同名组。标题模糊推荐和没有专用判别逻辑的同名组继续提供推荐，不执行正文 OCR。这样将额外识别限制在有明确判断依据的情况，避免扩大自动匹配范围。

标题判断分为已完成与需要正文两个结果。需要正文时，保留首次查询的候选和专用判别上下文，正文读取后直接完成判断或返回原推荐，无需再次查询标题。正文原文作为扫描记录的可选字段保存，比较时使用的规范化文本不覆盖原始观察。本轮不增加正文展示。

当前只支持「挂在竹子上的字条」，读取同一张截图的正文首行，不滚动。两份档案通过已核实的前缀区分，忽略排版空白、标点与遮罩，不用字符相似度自动确认。专用函数直接硬编码判断，不建立统一的前缀规则表，其他同名组未来可以使用不同的判断方式。

### 首行 OCR 标定

使用现有 PP-OCRv6 tiny 引擎及生产单行预处理，在 1280 × 720 截图 `018.png`、`019.png` 上验证 `ROI_LTWH(380, 118, 545, 36)`，分别得到「先祖保佑我家那口子」与「保佑寨子」。遮罩没有产生额外识别文字，两条已知前缀均可直接命中。首行区域纵向调整到 `(380, 115, 545, 45)` 或 `(380, 122, 545, 28)` 时结果相同，每个区域重复识别五次，文本均一致。

该标定只覆盖这两份同名档案的布局。单行已足以区分它们，无需依靠后续正文或字符模糊匹配。其他档案可能有两行标题或关联入口，新增规则时应同时核对正文区域。
