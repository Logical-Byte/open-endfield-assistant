# 档案匹配决策

领域含义见[术语表](GLOSSARY.md)，判定条件见后端[匹配模块](../src-tauri/src/automation/archive_scan/matching.rs)。本文记录设计原因与扩展约束，具体坐标、判别文本和档案标识以代码为准。

## 决策理由

- 每次档案详情页面只展示一个具体档案，因此每条扫描记录最多匹配一个档案。同标题无法证明是同一份档案，不能让一次观察贡献多个档案的收集证据。
- 只有能够唯一确认档案的证据才用于自动匹配。模糊候选即使只有一个，也可能只是目录中唯一足够相近的标题，不能据此认定已经收集。
- 匹配判断集中在后端，使领域判断拥有同一事实来源。前端负责用户选择，保留原始观察与后端建议，以便区分自动判断和人工决定。
- 用户明确清空匹配后，该记录应保持未匹配。因此，明确的人工未选择需要与尚未作出人工决定区分，避免自动建议覆盖人工决定。

## 正文判别的设计原因

额外的正文识别只用于有已验证判别依据的同名组。标题识别尚不能可靠限定候选时，再引入未经验证的正文推断，会扩大误匹配风险。将识别限定在已知同名组，也避免为其他档案增加无用的 OCR 开销。

标题判断与正文采集分成两个阶段，让匹配模块决定是否还缺少证据，扫描流程负责取得证据。两个阶段之间保留首次查询的候选与专用判别上下文，既避免重复查询，也保证后续判断沿用同一次标题观察的范围。标题和正文使用同一截图，防止页面变化使两者来自不同档案。

当前已验证的同名组使用首行即可区分，暂时没有必要引入多行定位或滚动采集。采用专用硬编码判断，是因为目前只有一个实际例子，尚不足以推导出适用于所有同名档案的统一算法。保留原候选作为无法确认时的结果，可以让自动识别失败后继续由用户判断。

供人工查看的参考正文与自动判别分开维护。展示文本的截取方式可能随可读性需求变化，不应连带改变自动匹配依据。参考正文仍只为人工选定的少量档案生成，避免携带全量正文带来的资源体积与维护成本。正文 OCR 原文单独保留，以便排查判断依据，规范化比较不覆盖原始观察。

## 扩展方式

新增同名组前，先核对源正文与稳定档案标识的关联，再用真实截图验证其可见文字与布局。正文来源和生成管线见[数据管线](data-pipeline.md)。遮罩可能显示为灰块，源文本换行也不一定对应屏幕换行，不能直接将展示用参考文本当作可靠识别依据。

在匹配模块中增加该同名组的专用判别方式，并将其正文区域和判断函数放在一起维护。判断方式由实际证据决定，不要求沿用现有组的前缀匹配。只有后续多个实例确实表现出共同规律时，再考虑提取共享逻辑。新增同名组不应要求扫描流程理解其文本特征或档案标识。

需要识别更多行时，先确认单行无法提供足够证据，再为对应判别方式增加逐行采集。两行标题、关联入口等布局差异都需要重新标定，不应将已有区域直接推广到其他详情页面。

通过匹配与扫描业务接口验证确认成功、无法确认时保留原候选，以及是否按需采集正文。开发截图用于人工标定，不作为集成测试的固定依赖，避免开发资源变化导致业务测试失效。
