# 档案匹配设计

本文记录已确认并实现的档案匹配设计。扫描流程参见 [档案库自动化](archive-automation.md)。领域定义见 [术语表](GLOSSARY.md)。

## 已确认的领域约束

- 每条扫描记录最多匹配一个档案。同一档案可以匹配多条扫描记录。
- 人工编辑直接回答扫描记录对应哪个档案，保留原始截图、OCR 文本与分类等观察。
- 候选档案不表示已经匹配，不作为已收集的证据。

## 自动处理

当前设计仅考虑标题，不加入正文 OCR。

- 规范化标题在扫描所在分类内精确命中一个 ID 时，自动建立唯一匹配，称为“自动的精确匹配”。
- 规范化标题精确命中多个 ID 时，仅推荐这些候选，不自动建立匹配。
- 没有规范化标题精确匹配时，模糊匹配仅提供推荐候选。推荐可以为空、一个或多个，不自动建立匹配。
- 当前只需支持电子档案分类的「文明」特殊规则，将其表达为对指定档案 ID `nar_digital_map02_13003_1` 的精确命中，不扩展为通用标题解释规则系统。
- 直接规范化精确命中优先于特殊规则。直接查找命中多个 ID 时也保留这些候选，不由特殊规则覆盖。仅在直接查找没有命中时尝试特殊规则。
- 模糊推荐保留相似度不低于 0.80 的全部标题组，不要求第一名与第二名存在最小分差。组内展开为具体档案 ID，按相似度降序排列，同分时按目录顺序排列，暂不设数量上限。
- 未来可讨论用正文等辅助证据区分同标题档案，本轮不设计或实现该能力。

## 模块职责与结果契约

- 规范化、精确匹配、特殊规则和模糊推荐保留在后端，集中在档案匹配模块内。
- 在类型层面区分唯一精确匹配与推荐候选，唯一精确匹配携带单个档案 ID，推荐候选携带零个、一个或多个候选。
- 前端消费后端结果并处理人工选择，不因推荐候选只有一个 ID 而自动建立匹配。
- 前端取消按同分类、同标题扩展匹配的规则，收集证据来自扫描记录当前生效的唯一匹配。

## 人工选择与界面

- 人工选择范围为扫描所在分类的全部档案，允许选择推荐候选之外的档案，不允许跨分类选择。
- 下拉框空输入时仅展示“推荐候选”和对应条目，不展示全部目录。开始输入后改为按标题子字符串筛选同分类档案。
- 点击或通过键盘进入输入框即展开候选，不显示单独的下拉箭头。输入仅用于按标题子字符串筛选，选择具体条目时使用档案 ID 建立关联。
- 人工选择持续优先，重新计算候选不覆盖人工选择。人工清除保持未匹配，不自动恢复匹配。
- 不提供清除选择或撤销人工选择按钮。用户删空输入并确认编辑后保存为人工未选择。原本唯一精确匹配的档案也加入推荐候选，用户可再次选择它，仍视为人工选择。编辑状态需区分“人工清除”与“没有人工决定”。

## 收集状态与导出

- 已收集档案是至少被一条扫描记录当前唯一匹配命中的档案，按 ID 去重。
- 其余目录档案均解释为未收集，包含仅成为候选但未被选择的档案。候选档案如果已被另一条记录匹配，仍为已收集。
- 未匹配记录不阻止地图导出。沿用现有 warning 提示用户未匹配记录的影响，不新增强制确认或忽略记录流程。
- 现有导出弹窗按未匹配扫描记录数量显示 warning，文案为“有 {{count}} 条扫描结果尚未匹配到已知档案。继续核对可能减少‘未收集’的数量，让导出结果更准确。”新模型中未选择记录计为未匹配，推荐候选不计入已匹配数量，沿用该提示及触发方式。

## 参考正文的数据范围

- 为帮助人工区分档案，在数据管线中加入可选的参考正文字段。
- 仅对人工指定的档案条目生成该字段，其他条目完全省略字段，不写入空值，控制资源体积和差异范围。
- 当前只保留正文第一行，不输出全文，不引入正文 OCR。
- 对启用的条目同时生成中英文首行，复用 `LocalizedText`。当前展示语言跟随游戏语言，使用中文。
- “第一行”指源正文的第一个非空文本行，以源换行符为界，不按游戏界面的视觉换行截取。提取时跳过空白行、处理显示用富文本标签，保留游戏原文中的遮罩。

## 已确认的界面方向

- 当前下拉选择原型已获认可，正式实现采用此方向。
- 右侧沿用“1 个匹配”的证据弹出框及定位操作，弹出框关闭、鼠标移开或来源卡片卸载时清除左侧高亮。
- 候选和匹配证据弹出框使用较明显的背景、边框与阴影，确保暗色主题下能与页面区分。
- 编辑先修改草稿，点击“确认编辑”后才更新档案归属和收集计数。“放弃编辑”恢复原有选择，删空输入同样需要确认。
- 已选框、下拉选项和左侧档案列表统一使用 `ArchiveLabel` 展示标题与可选的参考正文首行。两者紧接着放在同一行，用字号区分，正文使用灰色，整体超宽时以省略号截断，不换行、不分配固定的左右区域。
- 下拉选项不展示档案 ID，内部选择及匹配仍使用 ID。
- 原型界面使用中文，仅在原型期间切换界面语言，不写入设置。
- 沿用现有下拉框的自动定位行为，允许向上弹出，不加入空间判断或弹窗编辑。
- 原型直接复用现有扫描页面、卡片、筛选与计数，维持右侧“待核对”“已匹配”“全部”的布局。原型操作放在独立控制面板内，不在结果区域增加设计说明或状态调试文本。

## 实现位置

- 后端自动结果：`src-tauri/src/automation/archive_scan/matching.rs` 的 `MatchResult`，以 `exact` 与 `recommendations` 区分。
- 前端人工决定：`ScannedItemRecord.manualChoice` 区分自动、人工选择和人工未选择。`matchedArchiveId` 统一计算有效匹配。
- 展示与导出共用 `deriveArchiveMatching` 的 ID 关联规则，不按标题扩展。
- 数据生成：`scripts/data/tasks/contentPreview.ts` 中的人工白名单与首行提取，经 `makePrts`、后端投影和生成契约送达前端。

## 同标题案例的数据现状

「挂在竹子上的字条」的两个档案具有相同的标题、名称、分类与图标，均通过地图拾取获取。生成资源中可区分的字段为：

- `nar_paper_map02_93_1`：组内顺序 `1`，地图点位 `23300060006`。
- `nar_paper_map02_93_2`：组内顺序 `2`，地图点位 `23300060004`。

`prts.json` 保留组内顺序，`archive_contract.json` 保留地图点位。共享目录增加可选的双语 `contentPreview`，不增加组内序号或地图点位。

已通过 `PrtsAllItem.contentId → RichContentTable.contentList → I18nTextTable_CN/EN` 核实：

- `nar_paper_map02_93_1` 经 `text_sm2l3m1_1` 关联正文。中文首行为「先祖保佑我家那口子」，英文首行为「Protect my family」。
- `nar_paper_map02_93_2` 经 `text_sm2l3m1_2` 关联正文。中文首行为「保佑寨子■■■■」，英文首行为「Protect the ■■■■ Stockade」。

核实使用 [akedata 原表](https://data.akedata.wiki/manifest.json) 的 `1.5.3@10731330-8` 快照。本次生成与现有资源的全部条目字段一致，仅为上述两个档案补充可选首行。正文按源数据保留四个遮罩字符。
